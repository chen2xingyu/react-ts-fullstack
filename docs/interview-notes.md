# 证券交易系统 — 面试知识点

> 基于本项目可深挖的面试题与原理解析。每题都对应项目中真实的实现，可结合代码讲述。

---

## 一、架构与设计

### Q1：为什么撮合引擎用 Python，而资金结算用 Node.js？不能统一吗？

**项目做法**：Python 只管「算」（行情生成、撮合），绝不直写 MySQL；Node.js 只管「存」（事务落库、资金冻结），是数据权威；两者通过 Redis 解耦。

**设计考量**：
- **职责分离**：撮合是 CPU 密集 + 内存操作，Python 的 asyncio + SortedDict 适合；资金结算是事务密集，Node + mysql2 连接池更顺手。
- **安全性**：Python 进程无 DB 凭据，即使被攻破也动不了资金。真相源唯一在 MySQL，由 Node 事务保证。
- **可重启**：撮合引擎无状态（订单簿可从 Redis 快照重建），随时可杀重启，不影响资金安全。

---

### Q2：Redis Stream 和 Pub/Sub 都用了，为什么不统一？

| | Stream | Pub/Sub |
|---|---|---|
| 持久化 | ✅ 落盘，可回溯 | ❌ 发即弃 |
| 可靠性 | 消费者组 + ACK + pending 续消费 | 无 ACK，断线即丢 |
| 适用 | 交易流（订单/成交，不能丢） | 行情广播（最新即正确，丢一两个无妨） |

**项目映射**：订单/成交/撤单用 Stream（`stream:orders:new` 等），保证崩溃不丢；行情 tick/kline/depth 用 Pub/Sub（`ch:market:*`），追求低延迟、无需持久化。

---

## Q3：为什么资金/持仓的真相源在 MySQL 而不是 Redis？

Redis 即使有持久化，也不保证强一致（AOF/RDB 有窗口，集群分片有复制延迟）。资金是绝对不能错的金融数据，必须由关系数据库的事务保证 ACID。

项目里 Redis 只做「信使」（传订单/成交）和「缓存」（行情快照、活跃订单快照），**任何资金/持仓的增减都在 MySQL 事务内完成**。即使 Redis 全崩，MySQL 里的资金/持仓仍准确，重建 Redis 缓存即可恢复。

## 二、并发与事务

### Q4：如何防止并发下单导致的超卖/超冻？

**两道防线**：

1. **预校验**（友好提示）：下单前查 `cash_available` 是否够冻结，不够直接拒绝。
2. **事务内带条件 UPDATE**（真正防线）：

```sql
UPDATE accounts
   SET cash_available = cash_available - ?, cash_frozen = cash_frozen + ?
 WHERE user_id = ? AND cash_available >= ?
```

`WHERE cash_available >= ?` 让数据库做原子校验。并发时只有一个 UPDATE 能匹配，另一个 `affectedRows = 0` 即回滚。这比「先 SELECT 再 UPDATE」安全——后者在两次查询间存在竞态窗口。

---

### Q5：下单流程里冻结和落单为什么必须在同一事务？

若分开：先冻结资金（UPDATE accounts），再落单（INSERT orders）。若第二步失败，资金已冻但没单据，钱凭空消失。

项目把「冻结资金 + 插入委托单」放在同一个 `beginTransaction / commit` 内，任一步失败整体 `rollback`，保证「要么都成功，要么都不动」。

---

### Q6：撤单为什么不在发起时直接释放冻结，而要绕一圈经过撮合引擎？

**项目设计**：撤单只校验 + 投递 `stream:orders:cancel`，由撮合引擎从订单簿移除后产出 status 事件，Node 结算时才释放冻结。

**原因**：撮合引擎是订单簿的**唯一权威**。一笔部分成交的单子，簿中剩余量是多少、能否撤，只有引擎知道。若 Node 直接释放，可能与引擎簿中状态不一致（例如引擎刚好在成交这单）。让引擎裁决「还能撤多少」，再回传 status，保证一致。

## 三、容灾与可靠性

### Q7：撮合引擎崩溃重启后，挂单会丢吗？怎么解决？

**问题**：订单簿在内存（SortedDict），进程崩溃即丢失，所有挂单失效。

**项目方案：活跃订单快照 + 启动重建**
- **写入**：限价单落库后，同步写 Redis（`SET orders:active` 存 id 集合 + `HASH orders:active:{id}` 存字段）。
- **重建**：Python 启动时 `load_active_orders` 读回所有快照，`rebuild_from_active` 重建订单簿。
- **清理**：撤单/全成交时结算服务 `SREM + DEL` 清快照。

重启后挂单继续有效，可成交可撤。

---

### Q8：消费者崩溃后，已读未 ACK 的消息怎么办？

Redis Stream 的消费者组机制：消息读取后未 ACK 会留在 **pending 队列**，不会丢。

**问题**：原消费者崩溃，pending 消息无人处理。

**项目方案**（Redis 5 兼容）：消费者启动时先 `XPENDING` 扫描 pending 队列，对空闲超过阈值的消息用 `XCLAIM` 抢回归属重处理。

> Redis 6+ 有 `XAUTOCLAIM` 一步到位，但本项目环境是 Redis 5.0，故用 `XPENDING + XCLAIM` 两步替代，逻辑等价。

## 四、WebSocket 与实时性

### Q9：WebSocket 网关如何设计订阅路由？

- **连接鉴权**：连接时带 JWT，验证后才允许订阅。
- **房间订阅**：客户端发 `{type:'subscribe', symbol:'000001'}`，服务端把它加入该 symbol 房间；行情按 symbol 广播，只转发给订阅者。
- **私有通道**：成交/委托状态走 `ch:user:{uid}:notify`，定向推给对应用户。
- **心跳重连**：定时 ping/pong，断线指数退避重连，重连后自动恢复订阅。

---

### Q10：前端如何做到成交后即时刷新，而不是等轮询？

用 **React Query 的 `invalidateQueries`**。WS 收到成交/状态通知后，立即失效相关查询缓存（委托/成交/资金/持仓），React Query 自动重新拉取。

相比定时轮询：实时性更高（毫秒级 vs 秒级）、空载更少（无变化不请求）。3s 轮询作为兜底，WS 通知作为即时触发，两者互补。

## 五、风控

### Q11：你的风控有哪些维度？如何保证不留死角？

**12 类规则**：方向/类型/数量基础校验、标的有效性、手数、价格有效性、涨跌停、资金不足、持仓不足、幂等重复、撤单归属、撤单状态。

**保证留痕**：所有拒绝走统一的 `rejectRisk` 函数——「先记 `risk_logs`，再抛 RiskError」。收口到一处，新增规则只需调 `rejectRisk`，不会漏记。`risk_logs` 可查可聚合，前端有风控日志视图。

---

### Q12：幂等是怎么做的？

下单支持 `client_order_id`（前端生成的唯一键）。下单前查 `orders` 表是否已存在同 user + 同 client_order_id 的记录，存在即拒绝（`duplicate`）。

防止网络抖动导致的重复提交（用户连点、重试）产生多笔委托。

## 六、行情生成

### Q13：模拟行情用什么模型？为什么？

**几何布朗运动（GBM）+ 均值回归**。

- **GBM**：`dS = μS dt + σS dW`，是股价建模的经典模型（Black-Scholes 同源），能产生连续、波动合理的价格序列。
- **均值回归**：防止价格随机游走到离谱区间，拉回昨日收盘价附近。
- **涨跌停钳制**：超出 `prev_close ± price_limit_pct` 的价格截断，符合 A 股规则。

每秒生成 tick，tick 聚合成 1m K 线（OHLCV），同时维护五档深度。

## 七、工程化

### Q14：前后端类型如何保持一致？

- 后端定义统一响应结构 `{ code, message, data }`。
- 前端 `ApiResponse<T>` 泛型封装，`http.get<T>` 返回强类型。
- 交易实体（Order/Trade/Position 等）在前端 `types/trading.ts` 定义，与后端 Model 字段对齐。
- 常量（ORDER_STATUS/SIDE/TYPE）前后端各维护一份同值定义，注释标注「与后端对齐」。

**不足与改进**：理想方案是用 OpenAPI/Swagger 自动生成前端类型，消除手工同步。本项目规模小手工可控，后续可引入。

---

### Q15：这个项目最大的技术挑战是什么？

**撮合引擎容灾**。难点在于：
1. 跨进程一致性：Node（写快照）和 Python（读快照重建）是两个进程，快照格式、字段、清理时机都要严格对齐。
2. 时序问题：撤单后快照清理 vs 重建读取存在竞态——验证脚本里就遇到「撤单后快照未及时清除」的时序 bug，靠合理延迟 + 确认机制解决。
3. Stream 重投递去重：重建后重新消费 Stream，已处理过的订单要靠 `seen_ids` 集合去重，避免重复入簿。

最终通过 `verify-rebuild.js` 端到端验证：杀 Python → 重启 → 挂单仍有效可成交/可撤，资金守恒。
